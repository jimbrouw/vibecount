# Shared-refund database approval and reviewed connected reversal

17 October 2026. Local implementation, not deployment evidence. Shared-cash refund **database approval is implemented locally**. The human split-approval form is implemented locally; complete import-discard review is also implemented locally; hosted acceptance remains unfinished, so the shared-cash workflow is not ready for rollout. Existing one-original request fingerprints and result shapes remain compatible. See [split-refund-design.md](split-refund-design.md) for the coordinated posting, projection, report and export work still required.

## Current implementation

`lib/records/refund-splits.ts` validates a strict versioned split intent and calculates exact per-original cash portions and cumulative recognised reductions. Each portion retains the original category, project, percentage and source/year provenance; future negative effects use the refund date. Portions must sum to the entire observed cash. Any prior ordinary interpretation is removed once in the aggregate calculation, never once per portion. This model performs no write.

`lib/records/refund-closure.ts` traverses the active original/refund graph in both directions, including transitive sibling originals and their other refunds. It independently checks source ownership, endpoint/assignment counts, full cash allocation, effect provenance, original capacity and cumulative penny rounding. Refund cash is counted once per observation. Selected metadata is rebuilt into detached, allowlisted fields, without descriptions, raw evidence, storage paths or keys.

Migration `20261018050000_refund_closure_preview.sql` supplies the authenticated, owner-derived `read_refund_reversal_graph`. A stable snapshot returns complete safe metadata, independent counts and the financial context stamp. Import roots seed every owned observation in the import, including disconnected refund families. More than 20,000 observations, links or assignments rejects the whole read. The reference split catalog has a separate 10,000-observation/100-portion bound. Unsupported currency fails closed; the current source schema is GBP-only. Future FX semantics must be implemented explicitly rather than inferred; complete GBP import reversal is now coordinated by `18100000`.

Migration `20261018060000_reviewed_refund_closure.sql` adds `reverse_refund_closure`. It derives ownership from `auth.uid()`, locks the owner reconciliation scope, recovers exact completed requests before live checks, reconstructs the graph and checks the reviewed financial stamp. It locks source observations and child effects, rechecks currentness and refuses missing effects, inconsistent pointers, extra approved effects, invalid cash/rounding or any active invoice refund assignment.

All selected reversal rows, exclusions of every child negative effect, one Unknown decision/version increment per refund observation, cleared refund/pointer state and immutable request result commit together. Original payments are not updated; no earlier approval is restored. An import-root refund reversal does **not** discard the import. A late failure rolls back the entire action.

The old `reverse_refund_group` API retains its historical payload/retry semantics through a private `reverse_refund_group_v1`. Fresh legacy requests cannot reverse a shared component with unseen sibling originals. Such callers must use the complete review. The old import API consequently still fails closed on shared components. The application now uses the separate complete reviewed import coordinator (`18100000`), preserving legacy compatibility. This guard does not enable split approval.

## Reviewed database approval (`18080000`)

`approve_refund_split` accepts the same strict seven-field versioned intent as the pure calculation model: one refund/version/global financial stamp, 1–100 distinct original/version/group-stamp/exact-pence portions, rationale and request ID. It rejects extra fields, invalid types, duplicate originals, incomplete cash, foreign/stale sources, retained dependencies, invalid source/category/project provenance and inconsistent cumulative history. UUIDs are normalized and allocations sorted before the method-specific SHA-256 fingerprint; reordered exact retries recover the retained result before current source checks.

A revoked private writer serves both the new method and the legacy `approve_refund` wrapper. The latter preserves the exact old MD5 payload and four-field result, including approvals created by the actual predecessor migration. The owner reconciliation lock serializes governed actions. Selected bank observations, import states, records, category meaning and projects are locked in deterministic order and visible financial drift is rechecked. This is selected-write protection; unlike immutable tax capture it does not freeze every unrelated owner record through commit.

The migration replaces source-wide uniqueness with `financial_records_ordinary_bank_unique WHERE refund_link_id IS NULL`; unique refund-link effects remain. The ordinary classifier infers that partial index and never overwrites an excluded negative child. One prior ordinary interpretation is excluded once. Every nonzero portion inserts its own negative effect at the refund date, retaining its original category/project/type. Zero-recognised portions retain links without zero-value records. One aggregate Refund decision uses zero/null for percentage/category rather than inventing a shared treatment. The scalar posting pointer is cleared; a deterministic representative link signals dependency only. The result retains all child/source identities and separate cash, reductions, ordinary removals and signed deltas. Source observations and original positive records remain unchanged.

Before extending an original with prior refunds, a private validator follows the complete connected component and reuses reversal cash/effect integrity checks. Broken counterpart cash, markers, effects or sources fail closed. Original capacity and cumulative integer rounding remain bounded. All links, effects, prior exclusion, classification, source state and immutable request result commit or roll back together.

Fresh legacy one-original reversal now excludes child effects explicitly and records Unknown without depending on the scalar pointer. Its historical fingerprint/retry behavior and public shared-component guard remain. Invoice refund assignment validates the exact selected child and whole observed cash allocation; a child need not equal the representative marker. Per-refund, receipt-allocation, credit and invoice cash capacities remain, assignment posts zero income, and any sibling assignment blocks connected reversal.

## Human review

Eligible refund cash now links to `/dashboard/reconciliation/refunds/split?refund=…`. Its owner-derived atomic catalog (`18090000`) includes the selected observation and opposite-sign sources, bounded at 10,000 rows with no partial result. Only safe identity/date/money/accounting metadata and owned labels reach the form; the server rebuilds the allowlist and redacts bank-number patterns from labels. Descriptions, references, bank identifiers, raw evidence, paths and keys are omitted. Exact selected-source links retain owner/import scope and open transactions beyond normal pagination. Legitimate unselected draft records do not prevent catalog loading.

The form collects 1–100 explicit original/amount portions and requires the whole observed cash. It displays each category/project, source date, business percentage, remaining capacity, zero effect and invoice-correction need, plus aggregate reductions, ordinary removal once and signed profit changes in figures and words. Draft fields or refreshed props reset confirmation. The action validates strict normalized intent and human confirmation, checks owned request presence, and recomputes fresh reviews from server-read sources. Existing requests skip live reads but still call the database with the original intent for fingerprint verification; changed/cross-method requests cannot recover by ID alone. The writer rechecks currentness and complete history before committing.

Existing refund groups now link to `/dashboard/reconciliation/refunds/reversal?kind=original&id=…`. The page authenticates, reads authoritative graph metadata and withholds incomplete/foreign reviews. The form shows the entire connected scope, figures and words for cash counted once, income/expense reductions and signed profit changes, per-observation cash, all portions and source-import links. Sibling invoice assignments block the checkbox and button. A changed reason or refreshed graph remount clears confirmation. The action submits only the selected root, reviewed stamp, request and reason; client-supplied owner/link lists are not authority.

`kind=refund` reviews from refund cash; `kind=import` reviews all refund relationships connected to an import and explicitly explains that discarding the import is a separate action. No extra import is discarded, payment moved, invoice sent or tax submission made by this action.

## Complete-effect readers and versioned outputs

Migration `20261018070000_observation_accounting_effects.sql` prepares the read side without enabling split writes. `bank_transaction_record_effects` is a security-invoker, owner/bank-observation aggregate over all retained records. Approved signed amounts are summed independently for income and expenses; singular category/type/sign fields are populated only when homogeneous. Excluded records retain identity/history and contribute zero. A nonunique owner/bank index supports these reads. At this read-side migration checkpoint source-wide posting uniqueness remained unchanged; `18080000` replaces it with ordinary-only uniqueness.

The migration updates transfer/refund choices, receipt balances, duplicate review, the duplicate-aware import summary's base and explicit-owner filing input. Matching now reads the aggregate receipt bucket directly, removing its extra all-postings lookup and dependency on a scalar pointer. Each joins one aggregate per observation, avoiding multiplied transaction counts or financial stamps. Refund scope in the import summary follows all active connected originals/refunds, including transitive siblings and other imports. Tax observation/fact consumers inherit complete totals through duplicate review. The calculation reader retains each individual posting, with optional refund-link and project identity. Reconciliation stamp algorithms and their explicit-owner clones are unchanged because they already cover every posting/link.

Source exports independently page `financial_records` and `refund_links` through owner-constrained import relationships. They do not embed a potentially capped to-many posting array. Remaining nested source/reversal relationships are singular or uniquely constrained. Every source observation occupies one CSV row; version 2 appends complete safe effect/portion JSON, separate income/expense/profit totals and record counts. Singular compatibility columns are blank for multiple retained effects. `vibecount.evidence-manifest/2` uses `financial_records` and `refund_portions` arrays. Original source chains, categories, projects, excluded history, reversals and zero-recognised portions survive. Missing active portions/effects or failed pages reject the whole export. A financial stamp comparison and owned export-audit insert still precede response delivery.

New filing bundles use `draft-filing-pack/2`. The normalized ledger groups every selected-year posting by bank identity and sums all approved effects; cash remains one observation row. `year_financial_records` retains each posting's link, original, category/project and date. A selected-year posting whose physical cash observation is outside the year still contributes its accounting effect; its timing mismatch blocks completeness attestation rather than disappearing from the export. Missing posting-source observations reject the pack input entirely. Context observations without selected-year postings contribute zero.

The saved verifier accepts both bundle versions and returns original artifact bytes. `fixtures/legacy-filing-pack-v1.json` was generated by the predecessor implementation before these edits and verifies/exports unchanged. New database captures require version 2; unchanged retained requests are still recovered before live/version checks. Metadata additions change new calculation input bytes, so previously captured calculations may require a fresh current snapshot and downstream review before creating a new pack. Historical calculations and packs are not rewritten or regenerated.

## Reconciliation cash columns

`vibecount.reconciliation/2` appends columns after all existing fields. `refund_observed_signed_cash_pence` repeats source context per event; do not sum it. `refund_observed_signed_cash_once_pence` contributes on one deterministic non-reversal link row per physical observation, including retained/reversed/reallocated history. `refund_cash_portion_pence` is the individual event portion; `refund_active_cash_portion_pence` contributes only for current unreversed link rows. Reversal rows contribute zero observed-once/active cash and retain their signed accounting reversal. The complete export checks reciprocal source cash and full active allocation and never infers observed cash from a single portion. No saved filing artifacts are regenerated.
