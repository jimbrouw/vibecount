# Versioned invoice currency coverage in tax and filing review

18 October 2026. Adds a prerequisite for future external invoice capture. It does not enable external canonical invoices or FX financial settlement, certify tax treatment, or change tax rates.

## Current inputs and financial meaning

Forward migration `20261018200000_tax_invoice_currency_coverage.sql` adds a private, owner-parameter invoice coverage projection, called only through existing owner-derived tax/filing readers and trusted capture paths. It enumerates every owned finalised invoice, preserves complete counts, separately counts drafts, and classifies each finalised representation as native GBP with an available balance row, unsupported external, or invalid. Preserved external GBP is unsupported too: currency alone does not establish the evidence/settlement workflow. Exact compatibility decimals and original minor-unit strings, currency rules and captured source identities are retained as metadata. Descriptions, client names, invoice references, files, storage paths and encrypted contents are absent.

Coverage is explicitly **all owned finalised invoices, not tax-year income**. A document's issue date alone cannot establish cash-basis receipt timing or relevance to the selected year. Unsupported owner-wide context therefore conservatively blocks completeness until reviewed settlement/valuation and year relevance are supported. It neither adds original amounts to the ledger nor infers exchange rates, cash or GBP equivalence. Native balance availability proves representation/row coverage, not an independent recalculation of allocations or readable source evidence.

Current tax and filing inputs become `tax-calculation-input/2` and `filing-pack-input/2`. The coverage object has its own version and deterministic source token. Baseline `financial_stamp` semantics remain unchanged so existing profile/scope provenance is not rewritten. Current equality checks include the new object; calculation page reads the complete input again after loading history, including changes the old financial stamp may not cover. Missing, contradictory, foreign-owner or private coverage metadata withholds the review rather than defaulting to zero.

External/invalid coverage produces a blocking calculation issue and null affected profit, tax, NI, balance and payment estimates. Actual signed ledger amounts remain separately recorded; matching creates no income. SQL independently rejects an optimistic estimate or populated withheld totals. Filing review independently blocks completeness, and every new-version step digest includes the entire coverage context, so prior sources/income confirmations cannot survive changed invoice context. SQL rejects completeness even if a submitted bundle claims it.

Both tax calculation and filing pages show complete counts, explicit owner-wide scope, separately identified drafts and at most ten labelled unresolved examples. Available original values use their own currency exponent and figures/words. They are not displayed as GBP cash. Exact input/bundle hashes continue to bind the human confirmation surfaces.

New packs use `draft-filing-pack/3`. These metadata hashes do not prove current source availability. Historical V1/V2 packs continue to validate and return their original bytes. Legacy v1 calculation behavior and V2 pack generation from retained v1 input remain unchanged; new coverage logic is scoped to the new input version. Saved v2 calculation verification checks all withheld totals as well as stored byte integrity.
